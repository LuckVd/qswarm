## 3. 核心发现：题库答案键完整性缺陷（⚠️ 最高优先级）

### 3.1 现象与实锤

`scripts/build_seeds/build.py` 的变异（rename/reorder/dead_code/restructure）可以
**把漏洞本身变没，但 item 标签仍是 `planted: true / expected: real`**。实锤样例
`seeds/items/SEED-0006/snapshot/source.cpp`：污点参数 `data` 声明后零使用、
`_spawnv` 只执行固定宏常量（漏洞不存在），却残留 Juliet 模板 `/* POTENTIAL FLAW */`
注释（模式匹配的 giveaway）；变异器还把 `if (0) { /* dead */ }` 插到文件作用域
（非法 C 语法）。

### 3.2 启发式审计结果（`results/_bank_suspect_items.json`）

|---|---|---|---|

## 7. 操作手册与坑

```bash
# 在线播种（--cache-dir/--store-dir 缺省 = <out>/cache、<out>/store）
QSWARM_KEY_ZHIPU="$(cat .zhipu_key)" python3 -m qswarm.exams.seeding \
  --bank seeds/bank.yaml --models configs/models.zhipu.yaml \
  --db out/<run>/seeds.db --out out/<run>
# 离线重放（S9；不经网络，缓存未命中即停）
... --replay --cache out/<run>/cache/ --db out/<run>/replay.db --out out/<run>/replay-out
```

1. **坏响应会被缓存**（空串也是合法缓存值）：任何「修完管道再跑」都必须先修剪缓存
   ——用 `extract_json` 逐文件验证（本会话 v2 的修剪脚本逻辑：空/截断/解析失败一律删，
   只认生产解析器判定，勿用 `startswith('{')` 之类的粗判，会漏围栏内截断）。
2. **重考必须新 DB**：`exam_results` 幂等键 `(agent_id, purpose, item_id)` 查重跳过、
   存款有 `deposit_exists` 守卫——同库重跑只会静默复用旧判定。
3. **中断安全**：行+存款同格同事务，崩溃后同命令重跑即收敛（v1 续跑实证）；
   先用 sqlite3 backup API 备份（自动合并 WAL）。
4. 思考模式下单题 30s–3min，45 题串行 ≈2h；`runtime.exam_timeout_s=600` 后 v2 零重试。
   `reasoning_content` 不入缓存（缓存只存 content），要读思考需手动重调（协议：
   POST `{base}/chat/completions`，messages 用 `render_exam(...)` + `[{"role":m.role,"content":m.content}]` 装配）。
5. 出卷确定：`derive_seed(seed,"exam","entry-v1",agent_id,family,bank_version)`——
   同 (bank_version, agent, family) 恒同卷；换 bank_version 即全换卷。
6. 环境注意：本机 **无 git**（变更靠 DECISIONS + 证据文件追溯）；执行器单命令上限
   600s，长任务一律 `run_in_background` + 轮询；磁盘余 13G。
